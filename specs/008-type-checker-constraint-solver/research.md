# Research: Type Checker Constraint Solver

## Decision 1: Use Hindley-Milner style constraint generation with explicit TypeVar IDs

- Decision: Model unknown expression types as Type Variables with sequential IDs (`T1`, `T2`, ...), generated by a monotonic counter in checker state.
- Rationale: Matches spec requirements for deterministic behavior, supports polymorphic instantiation, and is easy to debug in logs/error messages.
- Alternatives considered:
  - UUID-based identifiers: rejected because non-deterministic and noisy for diagnostics.
  - Pointer-address identity: rejected because unstable across runs/build modes.

## Decision 2: Solve constraints with union-find + explicit occurs check

- Decision: Implement unification with disjoint-set union (path compression + union by rank) and perform occurs check before binding variable to composite types.
- Rationale: Near-constant amortized operations for large constraint sets and clear enforcement of recursive-type rejection (E2035).
- Alternatives considered:
  - Naive recursive substitution-only solver: rejected for weaker scaling on 100k constraints.
  - SAT/SMT backend: rejected as out-of-scope and introduces complexity/dependencies.

## Decision 3: Keep solver state fully in-memory and single-threaded

- Decision: Use in-memory structures (`ConstraintSet`, `UnionFindState`, `SubstitutionMap`) with no persistence and no internal synchronization.
- Rationale: Aligns with feature assumptions and constraint "all in memory", keeps implementation simple and deterministic.
- Alternatives considered:
  - Persistent/intermediate serialized constraints: rejected as unnecessary and slower.
  - Concurrent solver with locks: rejected (not thread-safe API by requirement).

## Decision 4: Error accumulation via ErrorType propagation

- Decision: On type failure, emit `CompileError`, assign `ErrorType` to failing subtree, continue generating constraints for the rest of the AST where safe.
- Rationale: Satisfies non-fail-fast requirement and reduces cascading noise while preserving maximal diagnostics.
- Alternatives considered:
  - Immediate abort at first error: rejected by FR-007.
  - Continue with unresolved raw type vars only: rejected because it amplifies cascaded errors.

## Decision 5: Zonking as explicit final phase over complete Typed AST

- Decision: After solving, traverse Partially-Typed AST and apply substitution to every node type (`TypePtr`) to produce Fully-Typed AST.
- Rationale: Clean phase boundary (Resolved -> Partially-Typed -> Fully-Typed) and easy verification in tests.
- Alternatives considered:
  - Incremental substitution during generation: rejected due to harder debugging and less deterministic diagnostics.
  - Lazy substitution on access: rejected because downstream phases expect concrete typed nodes.

## Decision 6: Integrate with existing Raw AST contracts in include/jsav/ast

- Decision: Constraint generation visitor must target concrete raw nodes in `Program.hpp`, `Expressions.hpp`, `Statements.hpp`, keyed by `NodeKind` enum.
- Rationale: Uses real AST surface already present in repository and avoids schema drift.
- Alternatives considered:
  - Introduce intermediate normalized AST: rejected (extra complexity, out-of-scope).
  - Partial node support first: rejected; scope requires all existing NodeKind.

## Decision 7: Testing strategy centered on runtime tests in test/tests.cpp

- Decision: Add scenario-based and integration runtime tests in `test/tests.cpp` for constraint generation, unification outcomes, zonking, and comprehensive error collection.
- Rationale: Explicit user constraint and repository preference for runtime coverage placement.
- Alternatives considered:
  - Separate new test file for runtime cases: rejected by user preference.
  - Property-based testing framework: rejected to avoid new dependencies.

## Decision 8: Logging strategy uses existing project logging format only

- Decision: Emit trace/debug/info logs through existing spdlog wrappers with project-standard formatting.
- Rationale: Required by FR-021/clarifications and avoids introducing telemetry schema.
- Alternatives considered:
  - Structured metrics endpoint: rejected by FR-022.
  - Custom logger backend: rejected (new dependency/surface).

## Decision 9: External interface contract is internal compiler API contract

- Decision: Define one internal module contract: `typeCheck(const Program&) -> pair<TypedProgram, vector<CompileError>>`.
- Rationale: Although non-public, this is a real cross-phase interface between semantic analysis and downstream compiler stages.
- Alternatives considered:
  - No contract artifact: rejected because interface is central and should stay explicit for downstream consumers.
